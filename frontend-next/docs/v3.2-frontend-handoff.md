## Result

One route-selected investigation owns the map, knowledge graph, evidence inspector, activity, findings and lifecycle. The complete workspace is keyed by case ID, so switching resets local selection, photographs, dialogue state, highlights and graph/map state. Navigation does not submit an investigation, pause a worker or send a field response.

The compact worker selector reads actual `worker.active_cases[]`, claim stages, capacity and availability. Background case streams remain case-scoped. A released claim leaves the selector even when its case awaits a rescan, evidence or a person. Stale closed-stream callbacks, older HTTP details and narration from another run are ignored. A new investigation clears the previous run's current findings, action, outcome and narration until refreshed source records arrive.

The existing collapsible operations rail now has **Waiting | Resolved** tabs. Both open the same investigation route. Waiting labels use authoritative case detail. Acknowledgement, acceptance and action success do not establish case resolution. V3.2 `action_status.resolution == VERIFIED_RESOLVED` governs green case resolution; older backends retain the verified-outcome fallback. Legacy brief/action text cannot override the newer lifecycle facts. Rejection, failed work, transport unavailability, expiry and late audit events have distinct presentations. Operational work does not become human judgment solely because the old workflow says HUMAN_REVIEW.

## Evidence synchronization

- Recorded `kind=tool_call` events appear separately, with their tool, stated question, sequence/time, source IDs and computed IDs. These are retrieval records, not model reasoning or verified findings.
- Following live retrieval reacts only to new recorded calls in the selected running investigation. Manual evidence inspection pauses follow; the operator can resume it. There is no timer-generated progress.
- Selecting a retrieval highlights exact current-case source nodes and their actual one-hop relationships. Clicking a graph source or a located map record opens the same inspector. Facility/device context follows real edges, without label or coordinate matching.
- Grounded map evidence is focused only when available. Route emphasis uses actual vehicle/route-run/trip identifiers on the existing segmented observations; no new line coordinates or parcel movement are generated. Planned route, observed vehicle telemetry and confirmed custody retain separate styling and labels.
- Retrieved records are no longer marked cited merely because the tool returned them. Recorded finding/recommendation/outcome citations remain distinct, alongside the existing independent-review and post-investigation-evidence presentations.
- Desktop is the primary experience, verified at **1440×900** and **1920×1080**. The map/KG height follows the desktop viewport, and the evidence column scrolls within that height. Existing Leaflet, React Flow/d3, resizable panels, map/graph focus controls, source photographs, Arabic, dark mode and reduced-motion behavior remain. The concept sketch did not replace the existing layout; no dedicated mobile experience was added.
- Synthetic data is visibly identified in the connected UI. No actual operator rescan is attributed merely because a qualifying routine read verified the request.

## API and request bounds

No backend endpoint or contract was changed. The base is `suhail-v3-1`, with additive `suhail-action-1` fields.

| Read | Consumer |
|---|---|
| `GET /worker/status` | Active claims, worker/stage selector, released capacity |
| `GET /cases/queue?scope=active` and `scope=resolved` | Separate cursor-paged queue scopes |
| `GET /cases/{id}` | Source nodes, edges, maps, findings, reviewer, lifecycle, outcome, decisions and next step |
| `GET /cases/{id}/events` | Actual recorded pipeline operations and separate narration events |

Queue paging remains capped at ten 100-item pages per scope; truncation remains visible. A poll enriches at most 24 unique case details, with at most three concurrent poll-enrichment requests. Explicit selected-case subscriptions and SSE state changes can also request deduplicated details. Eight waiting cases rotate per poll, including already-loaded cases because ACK/ACCEPT need not change case version. The open case and active workers are prioritized. In-flight details are deduplicated. Per-case detail refresh failures retain the last source snapshot with an explicit failure message.

Existing explicit decision/verification controls remain. There is no automatic POST on selection, viewing, highlighting or subscription, and this implementation never calls the synthetic action-response endpoint.

## Remaining limits and next actions

The current graph is bounded to 96 source nodes; the activity surface shows the latest 12 retrievals and up to 20 source buttons per operation. Other retrieved IDs remain visible as unavailable/counts rather than invented graph elements. Missing geography leaves the map unchanged. Existing full investigation records remain available in technical details.

Computed or cross-shipment result IDs are not automatically turned into source nodes. Stronger computed-result highlighting needs an explicit mapping such as `computed_source_ids: {result_id: [source_id]}` on the retrieval record. A bounded source lookup is needed only for evidence the API does not already serve; records merely cropped by the frontend need frontend expansion. Optional `case_id` on SSE frames would add envelope identity validation to the existing URL/run scoping. No such backend changes are included here.
